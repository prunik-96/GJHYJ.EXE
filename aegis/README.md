# aegis

Статический анализатор кода на Python: ищет уязвимости и ошибки **без нейросетей**.

Никакого обучения, никаких запросов в сеть, никаких зависимостей — только
стандартная библиотека. Результат воспроизводим: один и тот же код всегда даёт
один и тот же отчёт, и каждая находка сопровождается путём данных, который
можно проверить глазами.

```
python -m aegis .
```

## Зачем не нейросеть

| | Языковая модель | aegis |
|---|---|---|
| Повторяемость | ответ меняется от запуска к запуску | результат детерминирован |
| Объяснение | правдоподобный текст | конкретный путь данных по строкам |
| Выдумывание | возможно | исключено: находка либо выводится из графа, либо её нет |
| Скорость | секунды на файл | тысячи строк в секунду |
| Приватность | код уходит на сервер | ничего не покидает машину |

Слабое место у подхода тоже есть, и его честно стоит назвать: анализатор знает
только то, что в него заложено. Новый класс уязвимости он не придумает —
для этого нужно дописать правило.

## Архитектура

Шесть слоёв, каждый опирается на предыдущий:

```
исходный текст
      │
      ▼
  1. разбор ────────────► синтаксическое дерево (ast)
      │
      ▼
  2. разрешение имён ───► sp.run  ->  subprocess.run
      │
      ▼
  3. граф потока управления ──► базовые блоки и переходы
      │
      ▼
  4. поток данных ──────► неподвижная точка на решётке состояний
      │                    ├── помеченные данные (taint)
      │                    └── возможный None
      ▼
  5. правила по образцу ► криптография, секреты, настройки, типовые баги
      │
      ▼
  6. отчёт ─────────────► текст · JSON · SARIF
```

### 1. Разбор

Модуль `ast` из стандартной библиотеки. Синтаксическая ошибка не роняет
анализ — она сама становится находкой `AEG-PARSE-001`.

### 2. Разрешение имён — `core/symbols.py`

Правила написаны через канонические имена вроде `subprocess.run`. В коде это
может быть `sp.run`, `run` или `check_output`. Таблица псевдонимов собирает
импорты и убирает разницу. Она же отслеживает перекрытие: если в модуле есть
своя `def open(...)`, файловые правила к вызову `open()` уже не применяются.

### 3. Граф потока управления — `core/cfg.py`

Код разбивается на базовые блоки, между ними строятся рёбра. Обрабатываются
`if`, `while`, `for`, `try/except/finally`, `with`, `match`, а также `break`,
`continue`, `return` и `raise`. Рёбра ветвлений несут условие и его знак —
именно это даёт анализам чувствительность к проверкам.

### 4. Поток данных — `core/dataflow.py`

Классический worklist-алгоритм: состояния блоков пересчитываются, пока не
перестанут меняться. Циклы сходятся за счёт слияния состояний на входе в блок.
Жёсткий лимит раундов гарантирует завершение в любом случае.

Поверх решателя работают два анализа.

**Помеченные данные (`analyses/taint.py`).** Всё, что пришло извне,
получает метку. Метка течёт по присваиваниям, конкатенациям, f-строкам,
контейнерам и вызовам. Если она доходит до опасной операции — это находка.

Три вещи делают анализ точным:

- *Санитайзеры по категориям.* `shlex.quote` обезвреживает командную строку,
  но не HTML; `html.escape` — наоборот. Метка помнит, что именно уже проверено,
  поэтому `os.system("echo " + html.escape(x))` по-прежнему считается опасным.
- *Слияние путей.* Если значение обезврежено только на одной ветке `if`,
  проблема остаётся — и анализатор об этом сообщит.
- *Межпроцедурность.* За несколько раундов метка проходит через вызовы:
  сначала видно, какие функции получают грязные аргументы, затем их параметры
  тоже считаются грязными. Так прослеживается цепочка
  `обработчик -> помощник -> опасный вызов`.

**Возможный None (`analyses/nullness.py`).** Самая частая ошибка времени
выполнения. Анализ учитывает проверки: внутри `if m is not None` переменная
считается безопасной, `if m is None: return` снимает подозрение с остального
кода, `assert m` и `x = x or []` — тоже. Без этого правило давало бы шквал
ложных срабатываний.

### 5. Правила по образцу — `rules/`

Для проблем, которым поток данных не нужен: слабый хеш, пароль в исходнике,
отключённая проверка сертификата, изменяемое значение по умолчанию. Одно
дерево обходится один раз, обработчики вызываются по типу узла.

Точность держится на контексте, а не на поиске подстроки. Примеры:

- `random.choice(...)` попадёт в отчёт, только если результат уходит в
  переменную вроде `session_token`, — для выбора случайного цвета он безопасен.
- Строка в `PASSWORD` оценивается по энтропии и форме: `"a8Kd93Lm2qXzPw41"` —
  ключ, `"Введите ваш пароль"` — подсказка пользователю.
- `hashlib.md5(..., usedforsecurity=False)` не считается проблемой.

### 6. Отчёт — `report.py`

`text` — для человека, с путём данных и рекомендацией. `json` — для скриптов.
`sarif` — для GitHub Code Scanning и CI, с сохранением цепочки шагов
(`codeFlows`).

## Каталог проверок

34 правила. Полный список — `python -m aegis --list-rules`.

| Группа | Что ищется |
|---|---|
| `AEG-INJ-*` | внедрение команд ОС, выполнение произвольного кода |
| `AEG-SQL-*` | SQL-инъекции |
| `AEG-PATH-*` | обход каталога |
| `AEG-DESER-*` | небезопасная десериализация, `yaml.load` |
| `AEG-SSRF-*` | запросы по адресу от пользователя |
| `AEG-XSS-*`, `AEG-REDIR-*`, `AEG-XXE-*` | веб-уязвимости |
| `AEG-CRYPTO-*` | слабые хеши и шифры, отключённый TLS, предсказуемый random |
| `AEG-SECRET-*` | секреты в исходном коде |
| `AEG-CONF-*` | отладка на сервере, права на файлы, распаковка архивов |
| `AEG-BUG-*` | обращение к None, изменяемые умолчания, мёртвый код |

## Использование

```bash
python -m aegis .                              # проверить проект
python -m aegis app.py --format json           # машиночитаемый отчёт
python -m aegis . --format sarif -o out.sarif  # для CI
python -m aegis . --min-severity high          # только серьёзное
python -m aegis . --rule AEG-SQL-001           # одно правило
python -m aegis . --disable AEG-CONF-007       # выключить правило
python -m aegis . --fail-on critical           # когда ронять сборку
python -m aegis --list-rules                   # каталог проверок
```

Коды возврата: `0` — чисто, `1` — есть находки не ниже `--fail-on`,
`2` — ошибка запуска.

Подавить отдельное срабатывание можно комментарием в строке:

```python
os.system(command)              # aegis: ignore
os.system(command)              # aegis: ignore=AEG-INJ-001
```

## Как использовать из своего кода

```python
from aegis import Analyzer, Severity

analyzer = Analyzer(min_severity=Severity.HIGH)
for finding in analyzer.analyze_file("app.py"):
    print(finding.location, finding.title)
    for step in finding.trace:
        print("   ", step.line, step.description)
```

## Как добавить своё правило

Проверка по образцу — объявление и обработчик, регистрация автоматическая:

```python
from aegis.core.findings import Severity
from aegis.rules.engine import define, on

MY_RULE = define(
    id="AEG-CUSTOM-001",
    title="Отладочная печать в рабочем коде",
    message="вызов print остался в продакшене",
    severity=Severity.LOW,
    category="quality",
    remediation="Замените на logging.",
)

@on(ast.Call)
def check_print(node, context):
    if context.qualified(node.func) == "print":
        context.emit(MY_RULE, node)
```

Новый сток для анализа потока данных — одна запись в `analyses/taint_spec.py`:

```python
SinkSpec(
    names=frozenset({"mymodule.run_query"}),
    rule_id="AEG-CUSTOM-002",
    title="Запрос из непроверенных данных",
    message="значение из запроса попадает в текст команды",
    severity=Severity.HIGH,
    cwe="CWE-89",
    category="sql",
    remediation="Используйте параметры запроса.",
)
```

## Связка с языковой моделью

Модуль `aegis/ai/` скрещивает анализатор с Claude. Скрещивание не в том,
чтобы поручить поиск уязвимостей модели — это вернуло бы все недостатки, от
которых мы уходили. Роли разделены по сильным сторонам:

| | Языковая модель | Анализатор |
|---|---|---|
| Умеет | понимать намерение, писать код, объяснять | доказывать и опровергать |
| Не умеет | гарантировать правильность | догадываться |

Отсюда правило: **модель предлагает, анализатор решает.**

### Автопочинка с проверкой

```
находка -> запрос к модели -> патч -> ПРОВЕРКА -> принять или отклонить
                 ^                                      |
                 +------- причина отказа ---------------+
```

Патч принимается, только если проходит семь проверок разом:

1. разбирается синтаксически;
2. исходная находка исчезла;
3. новых находок не появилось;
4. определения верхнего уровня на месте;
5. правка локальна, а не переписывание файла;
6. не добавлен комментарий подавления;
7. тело функции не выпотрошено.

Проверки 6 и 7 — не паранойя, а необходимость. Вот реальный прогон, где
модель дважды «решила» задачу нечестно:

```
Попытка 1: ОТКЛОНЕНО
   - подавление: добавлен комментарий '# aegis: ignore'
   + находка устранена: AEG-INJ-001 больше не срабатывает

Попытка 2: ОТКЛОНЕНО
   - сохранность кода: тело backup() сжалось с 2 до 1 операторов
   + находка устранена: AEG-INJ-001 больше не срабатывает

Попытка 3: ПРИНЯТО
   + все семь проверок пройдены
```

Заметь: в первых двух попытках проверка «находка устранена» **прошла**.
Обе хитрости действительно убирали предупреждение. Наивная проверка
«исчезло ли сообщение» приняла бы их обе.

При отказе причина возвращается модели следующим запросом. Это работает
именно потому, что причина конкретна: не «неправильно», а «появилось
AEG-INJ-003» или «затронуто 80 строк при допустимых 40».

### Разбор находок

`--ai-triage` добавляет к находке вердикт и объяснение на человеческом языке.
Действует жёсткое ограничение: **модель не может отменить находку.** Она
только комментирует.

Причина не в недоверии ради недоверия. Анализатор ошибается предсказуемо:
правило либо покрывает случай, либо нет, и это проверяемо. Модель ошибается
непредсказуемо и при этом убедительно формулирует. Дать ей право вычёркивать
— значит поставить между разработчиком и настоящей уязвимостью текст, который
звучит уверенно и ничем не подкреплён.

### Использование

```bash
pip install anthropic
export ANTHROPIC_API_KEY=...

python -m aegis . --ai-triage            # разбор находок
python -m aegis app.py --ai-fix          # показать проверенные исправления
python -m aegis app.py --ai-fix --ai-apply   # и записать их в файлы
python -m aegis . --ai-fix --ai-attempts 5   # больше попыток при отказе
```

Без пакета и ключа всё остальное работает как прежде: связка необязательна,
ядро от неё не зависит.

### Своя модель

Нужен объект с одним методом:

```python
class MyProvider:
    def complete(self, system: str, user: str, max_tokens: int = 16000) -> str:
        ...

from aegis import Analyzer
from aegis.ai.autofix import AutoFixer

fixer = AutoFixer(MyProvider(), Analyzer())
outcome = fixer.fix(source, finding)
if outcome.success:
    print(outcome.patch)
```

Для тестов есть `ScriptedProvider` — отдаёт заготовленные ответы, позволяя
проверять связку без сети и без ключа. Именно на нём работают все 39 тестов
этого модуля, включая враждебные сценарии.

## Тесты

```bash
python -m unittest discover -s tests -v
```

135 тестов. Примерно половина проверяет, что анализатор **молчит** на
безопасном коде: для такого инструмента ложное срабатывание — такой же дефект,
как пропущенная уязвимость. Отдельный тест прогоняет анализатор по его
собственному исходному коду.

Файл `examples/vulnerable_demo.py` — образец с намеренными дефектами.
**Запускать его не нужно**, он существует только как материал для проверки.

## Границы применимости

Стоит знать заранее:

- Анализируется только Python.
- Поток между функциями отслеживается на несколько уровней вложенности, но без
  учёта контекста вызова: функция считается грязной, если хотя бы один вызов
  передал в неё непроверенные данные.
- Значения полей объектов и элементов словарей не различаются по отдельности:
  грязный элемент делает грязным весь контейнер.
- Динамика (`getattr` по вычисляемому имени, `exec`, подмена модулей) статике
  не поддаётся в принципе.
- Находка — повод посмотреть код, а не приговор. Уверенность каждой находки
  указана в отчёте.
